<!-- mid: 20261011-54ea | t: 2026-10-11 22:37:46 | p: pi-memory-auto | src: auto | tags: review-trigger,session-shutdown,stateless -->
Review triggering is stateless by design (replaces an earlier state-file counter approach): total turns are computed each round from `sessionManager.getBranch()` (count user+assistant messages ÷ 2) and trigger at integer multiples of reviewTurns — no persisted counter, so reload/resume can't reset it, and compaction entries (not counted as messages) stay in the branch so pre-compaction turns still count. Memory flush extraction runs only on `session_shutdown` with `reason === "quit"` (pi awaits this handler; cap at ~30s via LLM_TIMEOUT_MS so quit isn't blocked); reload/new/resume/fork do not trigger. Possible overlap with periodic extraction (flush shortly after a periodic run) is mitigated by dedup plus feeding only the branch tail (~20 entries) to the flush prompt; skip flush if <4 messages.

MEMORY.md 的归属最终定调（用户的答复推翻了「自动区 + 手写区」双区方案）：MEMORY.md 必须**完全由程序自动写入和编辑**，用户在正常使用中永远不需要、也不应该直接接触它；每次保存记忆写关键词时都要同步落一份，build / rebuild / compact 之后同样要重新同步；注入上下文给模型的就是这份文件的内容，不再保留「从分类文件现算 `collectKeywords()`/`renderKeywordTable()` 再拼 preamble」的第二条渲染路径。缺了这份同步正是 0.4.0「MEMORY.md 从未被创建 → 注入空块」事故的成因。另外 `src/search.ts` 里把 MEMORY.md 当数据源解析、并给 `+0.5` 打分的代码是从未生效的死代码（关键词行没有 `<!-- mid:` 元数据），应在改造时删掉以免再次误导。

pi-memory-auto v0.7.1 的实际实现（修正「注入即读 MEMORY.md」的旧理解）：`loadAllEntries()` 只读六个分类文件，`index-map` 显式跳过 `MEMORY.md`，`before_agent_start` 仍从分类文件现算 `collectKeywords()`/`renderKeywordTable()`，**注入时从不回读 MEMORY.md**。因此 MEMORY.md 是程序独占的落盘副本，过期只是观感问题，但要求所有写路径必须 await 落盘：`index.ts` 里原来的 `void refreshIndexes(ctx)` / `void materializeAll(...)` fire-and-forget 已改成 `syncIndexesNow()`（= `await materializeAll` + `maybeConsolidate`），保证 `memory_write`/shutdown 返回时关键词已经写进文件。同时删掉 `search.ts` 中把 MEMORY.md 当数据源的解析、`curated` +0.5 打分和 `pathJoin` 死代码——它们让人误以为索引文件可以手写条目。

<!-- mid: 20261024-c522 | t: 2026-10-24 02:03:03 | p: pi-memory-auto | src: user | tags: 遗忘策略,supersede,staleness -->
pi-memory-auto 0.8.0 的「遗忘」只有两级，且都零数据风险：(1) supersede 软失效 — memory_write 的 supersedes:[id] / extractor 的 SUPERSEDES: 行给旧条目加 metadata `superseded-by`，旧行保留、正文不动，但退出 MEMORY.md 关键词表、在 search 里永远排最后并标注；(2) staleness 复查 — 按文件类型给周期（TOOLING 3 月 / USER·CONVENTIONS 6 月 / LESSONS·FAILURES·DECISIONS 12 月），从 entry 自身时间戳（re-confirm 后取 `last`）现算，不落新字段、不迁移，到期只在搜索结果里降权并标注 stale，绝不删除。明确否决自动删除/decay/eviction：调研里 agentmemory、mcp-memory-service 的淘汰都把记忆生死押在 LLM 打的 importance 分上，分数漂移就静默丢数据；判断「这条还有替身吗」是确定性系统能做的，判断「这条还有用吗」不是。

<!-- mid: 20261024-5d1e | t: 2026-10-24 02:03:03 | p: pi-memory-auto | src: user | tags: 写入幂等,usage-log,关键词排序 -->
pi-memory-auto 0.8.0 的写入与索引侧三个确定性机制：写入幂等 —— `normalizeMemoryText`（仅忽略大小写/空白/尾部标点）后在同层三个分类文件里找同文条目，命中则不新增行，只在 meta 上加 `seen: N | last: <time>`（seen===1 时省略字段，保持旧条目字节不变）；usage 边车 —— `memory_search` 第 1 页命中时把「查询里出现且命中条目携带」的关键词计入 `<layer>/usage.json`（不是记忆条目、不参与注入），索引排序改为 `count + min(recalls,4)`，且 usage 故意不作为重新渲染触发点（否则每次搜索都会打穿 prefix cache）；索引预算耗尽时分级降级 —— 先摘掉 `(count)` 后缀把剩余关键词塞进续行，实在放不下才写 `(+N more — memory_search mode:"keyword")`（旧提示指向 mode:"recent" 是最弱检索）。

pi-memory-auto adoption plan distilled from docs/open-source-agent-memory-survey.md, agreed priority order **A1 → A4 → A2 → A3 → B2 → B1**. A1: write-time idempotency in src/store.ts — normalizeHash(lowercase/collapse whitespace/strip punctuation) before append; on same-file hit do NOT add a row, rewrite meta with `seen=N` + `last=DATE` (parseMetaLine/serializeEntry ignore unknown fields, so backward compatible); cuts entry churn, consolidation triggers and LLM cost, and `seen` doubles as a strength signal. A2: supersede soft-invalidation — meta `supersedes: <mid>` / `superseded-by: <mid>`; superseded entries filtered out of index-map.collectKeywords (no index slot), downranked + labelled "(superseded by X)" in search, but the original bytes are never deleted; extractor emits a `SUPERSEDES:` line restricted to mids present in the existing-memories digest. A3: `memDir/usage.json` sidecar recording keyword hit counts from memory_search (atomic write, fire-and-forget, never injected, never inside memory files); index ordering = count + usage boost, budget favours high-hit/count≥2 keywords. A4: /memory report adds stale count, never-recalled keyword count, near-duplicate candidate pairs (keyword Jaccard + text token overlap, threshold 0.6, flag-only like claude-mem Tier-1), superseded count — makes consolidation targeted instead of blind whole-layer LLM runs. B-tier (deferred): B1 engram-style `review_after` re-review reminders that only downrank + tag "stale since X", never delete; B2 claude-mem-style graceful degradation (full → drop count=1 → count≥2 + hint, or comma-pack count=1 keywords) instead of a single truncation to "(+N more)"; B3 pin/full-body injection section (~800 chars), skipped for now. Explicitly rejected: timed TTL / hard eviction, letting the LLM decide UPDATE/DELETE (mem0 v2 reverted to ADD-only), per-tool-call observation compression, vector retrieval, decay curves — the project has no reliable `importance` upstream signal, so copying them turns error into data loss. Overarching rule: when config parsing fails or state is uncertain, never clean up / never mutate.
